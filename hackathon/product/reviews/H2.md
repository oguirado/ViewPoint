## Ranked findings

### BLOCKER

**B1 — `wait-event` matches the first close for an `event_id` anywhere in an append-only log, so an old receipt can produce a false success.**
- Citations: `swarm/agents/intent_cli.py:516` (tail starts at `offset = 0`), `swarm/agents/intent_cli.py:539-549` (returns on the *first* matching `close`); `swarm/agents/prompts.py:119`, `swarm/agents/prompts.py:120`, `swarm/agents/prompts.py:123` (hard-coded ids `camera-agent-gui-1`, `camera-agent-gui-1-r1`, `camera-agent-gui-2`); `swarm/agents/prompts.py:25` (`<unique_id>` with no run scoping). Cross-ref: `swarm/broker/broker.py:319` opens `events.jsonl` in append mode and never truncates it; `swarm/broker/broker.py:298` keeps `seen_event_ids` only in memory.
- Failure: the default `SWARM_EVENTS_LOG` (`swarm/run/events.jsonl`) persists across broker runs. In a second run (or any reuse of an id), the camera brief's fixed ids already have a `VERIFIED` close from the earlier run. `wait-event` returns that old receipt with rc 0 straight away. Meanwhile the new intent is refused with `DUPLICATE_EVENT` (same broker process), or runs later with nobody watching (restarted broker). Reproduced in `/tmp`: a log with `VERIFIED` and then `DUPLICATE_EVENT` for `camera-agent-gui-1` gives `verdict: VERIFIED`, `rc=0`. The same thing happens inside a single run whenever an LLM reuses an id after a refusal. This breaks the §3.1 idempotency semantics and makes the only success signal agents have untrustworthy.
- What the Gemini writer must change: `wait-event` should only accept a `close` written *after* this enqueue. Options: record the log size (or the last `tick`) at enqueue time and start tailing from there; or require the matching `enqueue` record (same `event_id` plus `script_sha256` / `created_ts_ms`) to appear first and only take the `close` that follows it. When the matched close is `DUPLICATE_EVENT`, return a distinct non-zero code. Every event id in `prompts.py` must carry the run id that `build_brief` already receives (e.g. `<run_id>-camera-agent-gui-1`), and the shared prefix should require run-scoped ids for LLM-chosen ids too. Add a negative-control test: a pre-existing `VERIFIED` close plus a fresh `DUPLICATE_EVENT` must not give rc 0.

### MAJOR

**M1 — The runner's 6G/8G memory scope does not apply to `agy`: the shim moves the process into a new 12G/16G scope.**
- Citations: `swarm/agents/runner.py:25` (`AGY_SHIM = ~/.local/bin/shims/agy`), `swarm/agents/runner.py:53-76` (outer `systemd-run --scope` 6G/8G); `swarm/agents/README.md:14` (says the agents run inside the 6G/8G scope). Cross-ref: the shim runs `exec systemd-run --user --scope --slice=newton-ia.slice -p MemoryHigh=12G -p MemoryMax=16G ...`.
- Measured: under the same outer scope, the outer process's cgroup is `app.slice/run-r768f….scope`. After the shim's nested `systemd-run --scope`, the process sits in `newton.slice/newton-ia.slice/run-r3633….scope` with `memory.max = 17179869184` (16 GiB). A scope is not nested inside the scope of the process that started it, so the 6G/8G cap does not hold. Four agents can reach 4 × 16 GiB next to Blender.
- What to change: make the 6G/8G cap actually apply to the `agy` process. Either call the real binary (`~/.local/bin/agy`) directly inside the runner's scope and set `GOMEMLIMIT` yourself, or pass the 6G/8G properties through the shim's own scope (that needs an operator decision, because the shim is outside `swarm/`). Add a dry-run or live assertion that reads `/proc/<pid>/cgroup` and the matching `memory.max`. Fix the README claim.

**M2 — `write_set` declarations understate what the scripts change; cross-claim writes get past the only oracle (§8.1).**
- Citations:
  - `swarm/agents/scripted_smoke.py:123-126` and `swarm/agents/prompts.py:52`: `modeler-agent` hides the factory `Cube` (`obj:Cube`, outside `col:CHAR_`/`obj:CHAR_`). The smoke check (8 vertices) also skips the "at (0,0,0), untouched, no PROP_ inside" conditions the brief states.
  - `swarm/agents/scripted_smoke.py:243-266` and `swarm/agents/prompts.py:98`, `swarm/agents/prompts.py:104`: `look-agent` clears and rebinds material slots on `CHAR_*` / `PROP_*` mesh data owned by `modeler-agent` / `props-agent`. This contradicts the shared-prefix invariant at `swarm/agents/prompts.py:31` ("NEVER ... mutate Blender objects ... outside your prefix").
  - `swarm/agents/scripted_smoke.py:279`, `swarm/agents/scripted_smoke.py:303`, `swarm/agents/scripted_smoke.py:311-315`: `look-agent` sets `scene.world`, links lights into `scene.collection`, and writes `scene.render.engine` plus `scene.eevee.*`. `render:` belongs to `camera-agent` (§4.1).
  - `swarm/agents/scripted_smoke.py:340` with `swarm/agents/scripted_smoke.py:525`: `camera-agent` sets `scene.render.engine` but declares only `cam:MainCam`.
- Why it matters: §5.1 defines `write_set` as "resource keys mutated", and §8.1 makes prefix enforcement on `write_set` the only script-lane safety oracle. The broker cannot see writes that are not declared, so disjointness holds on paper but not in the scene. Today the clashes happen to be benign (everyone sets EEVEE), but the briefs teach the LLM agents that undeclared cross-claim writes are fine.
- What to change: remove `render:` writes from `look-agent` (leave bloom/AO/engine to `camera-agent`, or put them in a camera `render:` turn). Remove the `Cube` hide from `modeler-agent`, or move it to an owner the contract allows. Material binding onto other agents' meshes needs a contract ruling (H0) before H2 can be compliant: either the contract says `mat:` ownership includes slot assignment on any mesh, or modeler/props assign materials by name themselves. Until then, `prompts.py:98` and `prompts.py:31` contradict each other and must be reconciled. Every script's `write_set` must list everything it mutates within its own prefixes (e.g. `render:engine`).

**M3 — The STALE_FRAME "re-enqueue with a new id" strategy fights the contract's tail-requeue. It leaves ghost events that burn turns and write `park` records to the authoritative log.**
- Citations: `swarm/agents/scripted_smoke.py:570-605`; `swarm/agents/prompts.py:35`, `swarm/agents/prompts.py:120`, `swarm/agents/prompts.py:124`. Contract §3.1 TURN GUI step 3 ("return event to the agent's tail. At `drops == 3`, park the event and emit `refute`"). Cross-ref: `swarm/broker/broker.py:928-960`.
- Failure (traced through the broker code, not run live): the broker keeps the stale original in the camera FIFO and also receives the new `-rN` copy. The original can never pass (its `based_on_frame` is fixed and `head_frame` only grows), so it uses up to two more camera turns. Then it emits `STALE_FRAME` plus a `control` `op:"park"` record (a `refute` projection) for every stale GUI pass. Liveness: every builder `close` captures a new frame, so a camera GUI intent enqueued while builders are still active is stale on almost every camera turn. Traced for the 4-agent smoke: `c2-gui` is first accepted on about attempt 3 of `max_attempts = 4` (`scripted_smoke.py:570`), with one attempt to spare. Live LLM pacing is less predictable, and the brief gives no retry budget.
- What to change: choose one retry model and line it up with H1. Either (a) do not mint a new id on `STALE_FRAME`; keep tailing the same `event_id` for its next `close` (the broker requeues it), which only works if staleness can clear, i.e. a `rebased` path or `--auto-rebase-viewport` agreed with H1; or (b) enqueue GUI passes only after the builders go quiet (reuse the `after_builders` gate at `scripted_smoke.py:546` for the GUI steps and say the same in the camera brief). The test mock should model tail-requeue (see m5).

**M4 — The 180 s `wait-event` default is shorter than the contract's worst-case queue latency, and a timeout looks the same as a hard error.**
- Citations: `swarm/agents/intent_cli.py:511`, `swarm/agents/intent_cli.py:718`, `swarm/agents/intent_cli.py:733-735` (rc 1, `TIMEOUT`); `swarm/agents/prompts.py:27` (`--timeout-s 180`); `swarm/agents/scripted_smoke.py:621`, `swarm/agents/scripted_smoke.py:718` (`builders_done.wait(timeout=timeout_s)`).
- Derived from §3.1: three other ring agents at up to 120 000 ms each, plus the agent's own 120 000 ms job, comes to about 480 s before a legitimate `close` [DERIVED]. A `wait-event` timeout returns rc 1, the same code as `CLAIM_REFUSED`/`JOB_ERROR`, and the brief gives no instruction for it. An LLM agent that re-enqueues after a timeout duplicates a non-idempotent GUI act, or a script that is still in flight.
- What to change: base the default on the contract caps (at least ring size × 120 s plus a margin), give timeout its own exit code, and add a brief rule: after a CLI timeout, re-run `wait-event` on the same id and never re-enqueue.

**M5 — TaskLight `post_step` can be posted twice (agents and H4 projector), which breaks §7.2 "Exactly one microtask per `close` receipt".**
- Citations: `swarm/agents/prompts.py:38` (agents told to `post_plan`/`post_status`/`post_step`/`close_task` themselves "or" rely on the projection). Cross-ref: `swarm/projection/projector.py:267-277` already posts `post_step` per close.
- What to change: give TaskLight a single owner. If H4 owns it, remove the agent-side `post_*` instructions (keep at most `close_task` if H4 does not send it) and say H4 owns them. If agents own it, H4 must stop. Either way the shared prefix must state one rule, not "or".

**M6 — `--kill-all` can signal recycled, unrelated PIDs; pid files are never removed.**
- Citations: `swarm/agents/runner.py:115` (`run_*.pid` with no `--run-tag` matches every historical run), `swarm/agents/runner.py:120-158` (SIGTERM then SIGKILL with no identity check), `swarm/agents/runner.py:243`, `swarm/agents/runner.py:250-254` (pid file written, never deleted after exit).
- Failure: after any finished run, `swarm/proof/run_*.pid` still names a dead PID. After PID wraparound, `--kill-all` sends SIGTERM and then SIGKILL to whatever process now has that number, possibly Blender (`vpswarm`) or another AI session. SIGTERM also only reaches the scope's main PID, not the `agy` child tree.
- What to change: before signalling, check identity (`/proc/<pid>/cmdline` contains the agy binary, or the start time in `/proc/<pid>/stat` matches a value recorded at launch). Delete or rename the pid file once `proc.wait()` returns. Give each scope a deterministic `--unit` name and stop it as a unit (`systemctl --user stop <unit>.scope`) so the whole tree is cleaned up without broad pattern kills.

### MINOR

**m1 — `wait-event` maps `NO_VISIBLE_CHANGE` to the same rc 3 as `STALE_FRAME`.** `swarm/agents/__init__.py:52`, `swarm/agents/intent_cli.py:547-548`. `NO_VISIBLE_CHANGE` is an *executed* act (`tick + 1`, §6), whereas `STALE_FRAME` is a refusal that is requeued. An LLM that sees rc 3 and follows the "re-enqueue with new id" rule (`prompts.py:35`) repeats the act blindly, which §3.1 forbids. The smoke checks the verdict string (`scripted_smoke.py:603`), but the CLI contract should use separate exit codes.

**m2 — The brief does not cover all verdicts.** `swarm/agents/prompts.py:34-36` lists 7 of the 18 §6 codes. It has no guidance for `FRAME_EVICTED` (contract: full re-observe), `LEASE_EXPIRED`, `NO_LEASE`, `TURN_TIMEOUT`, `QUEUE_FULL`, `DUPLICATE_EVENT`, `FOOTPRINT_MISSING`, or the CLI's own `TIMEOUT`. Add one line per code saying re-observe, wait, or stop.

**m3 — Agent identity is not bound.** `swarm/agents/intent_cli.py:681`, `swarm/agents/intent_cli.py:697` let any process pass any `--agent`. §2 says "Each agent writes ONLY inside its own `<agent_id>/` subdir". The runner could export a per-role identity variable, and the CLI could refuse a mismatched `--agent`.

**m4 — `--demo-stale-rebase` can pass without demonstrating anything.** `swarm/agents/scripted_smoke.py:576-577`: if the observed frame is `0`, `max(0, frame-1)` equals the head frame, so no `STALE_FRAME` happens. If `frame-1` was evicted from the 64-frame ring, the step gets `FRAME_EVICTED` and the smoke aborts. The demo should check that at least one `STALE_FRAME` receipt was seen.

**m5 — The test mock broker differs from the contract, so B1 and M3 are untested.** `swarm/agents/test_agents.py:460-462`: on `STALE_FRAME` the mock advances `tick` and drops the intent, but the contract requeues at the tail with `drops + 1`, parks at `drops == 3`, and leaves `tick` unchanged on refusals (§6). No test covers a reused `event_id` or a persistent log.

**m6 — Malformed `latest.json` crashes with a traceback instead of a JSON error.** `swarm/agents/intent_cli.py:95` only checks for `frame`, while `intent_cli.py:398-399`, `intent_cli.py:455-456`, `intent_cli.py:494-495` index `view_epoch`/`scene_epoch`. `main` catches only `IntentValidationError`/`TimeoutError` (`intent_cli.py:728-735`). Validate the full §2.2 sidecar keys up front.

**m7 — Lease expiry is never checked client-side.** `swarm/agents/intent_cli.py:163` exposes `expires_ts_ms`, but `build_script_intent`/`build_gui_intent` (`intent_cli.py:385`, `intent_cli.py:438`) enqueue regardless, so expired leases only show up after a full ring wait as `LEASE_EXPIRED`.

**m8 — The deliverables script changes session-global state.** `swarm/agents/scripted_smoke.py:372` (`save_as_mainfile` without `copy=True`) makes the live session's file path point at the deliverable `.blend`, which affects later saves and §3.3 checkpoint semantics. `scripted_smoke.py:373-386` runs `export_scene.gltf` and `render.render` from the bridge's `bpy.app.timers` context, and there is no Blender 4.0.2 evidence in the corpus that these operators succeed there (AUSENTE — no inventar). A timing budget against the 120 s cap is also missing.

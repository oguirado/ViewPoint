## Findings (ranked)

### BLOCKER

**B1 — The `:1` hard gate is bypassed by leading zeros (`:01`, `:001`, `host:01.0`, …).** `swarm/tools/record.sh:44-57`
The gate extracts the display number as a string (`DISP_NUM`, line 46), checks only that it is all digits (line 48), and compares it to `"1"` as a string (line 54). X11 clients (libxcb/Xlib, used by `ffmpeg -f x11grab`) parse the display number numerically, so `:01` connects to display 1.

Reproduced on a private server, never on `:1`: with `Xvfb :9187` running, `record.sh ":09187" p4h3alias` returned rc 0, ffmpeg recorded the 1920x1080 Xvfb screen for 2.13 s, and `xdpyinfo -display :09187` opened the same server [MEASURED]. The same input shape, `record.sh :01 <name>`, therefore records the reserved operator display `:1`. That breaks the invariant stated in `README.md:215` and in the brief ("unconditionally refuse `:1`").

The same flaw lets `:00` skip the `--allow-display0` guard (`record.sh:60`). The negative-control test (`test_overlay.py:875-902`) covers only literal `:1` forms, so it does not catch this.

Required fix (prose): normalise the parsed display number to an integer, base 10 with leading zeros stripped, before both comparisons. Add `:01`, `:001` and `:00` cases to the negative-control test.

### MAJOR

**M1 — In `auto` mode the timeline heuristic overrides the authoritative sidecar and maps a multi-run log onto the wrong window.** `swarm/overlay/compositor.py:383-423`, `426-430`
`events.jsonl` is append-only across broker runs. The broker opens it with mode `"a"` and never truncates it (`broker.py:316-320`, default path `broker.py:41`). `resolve_timeline` accepts the `record.sh` sidecar only if at least 25 % of all non-claim event timestamps fall inside the video window (`compositor.py:417`). It then tries file mtime at 50 % (`compositor.py:420`), and otherwise falls back to `span` over **every** event in the file (`compositor.py:423`).

Reproduction: 80 events from an earlier run, plus 20 events from a run one hour later that the sidecar matches exactly. `resolve_timeline` returned `(999880, 4891132, 'span')`: a 64.9-minute window stretched over a 10 s video [MEASURED]. Every cursor and strip state is mis-timed, with no warning.

The same fallback triggers whenever a recording starts late and covers less than 25 % of a single run. The sidecar from `record.sh:86-88` is the only real wall-clock anchor. It should win whenever it exists, and the heuristic `span` fallback should be opt-in or at least logged.

**M2 — An event-level park is rendered as a permanent agent-level `[PARK]`.** `swarm/overlay/compositor.py:596-600`, `613-622`
After three `STALE_FRAME` drops the broker parks only the **event**. It emits `control op:"park"` with `reason:"parked_after_3_stale_drops:<event_id>"` and keeps scheduling the agent (`broker.py:946-964`; CONTRACT §3.1.4 "park the event"). The tracker adds the whole agent to `parked_agents` twice: on `drops >= 3` (line 599), and again by substring-matching an agent id inside `reason` (lines 620-622, which match because event ids embed the agent id). Only an untargeted `resume` clears it (line 625).

On the real log, the tracker ends with `parked_agents = ['camera-agent']`, yet the broker gave `camera-agent` 4 more turns after the first event park [MEASURED]. The demo video therefore shows `camera-agent [PARK]` in the queue strip while that agent keeps acting.

The agent-level park that the contract does define (2 consecutive `TURN_TIMEOUT`, `broker.py:790-801`) should be detected from its `reason` pattern, or better from an explicit field. That needs a contract amendment, because the CONTRACT §5.2 `control` schema has no `agent_id`.

**M3 — Possible encoder deadlock: the ffmpeg stderr pipe is never drained while frames are written.** `swarm/overlay/compositor.py:1109-1114`, `1186`, `1195`
`stderr=subprocess.PIPE` is read only after `stdin` is closed (line 1195). ffmpeg writes a progress line roughly every 0.5 s, measured at **345.5 B/s** of stderr while encoding at this command's settings [MEASURED]. The default Linux pipe holds 64 KiB, which fills after about **3.2 min of encode wall time** [MEASURED, extrapolated]. ffmpeg then blocks on stderr, stops reading stdin, and `encoder.stdin.write` (line 1186) hangs forever with no timeout.

Mechanism check: with the stderr pipe shrunk to 4 KiB via `F_SETPIPE_SZ`, composing a 120 s / 1800-frame input hung until it was killed at 150 s (rc 124). The unmodified control finished the same input in 15.5 s (116 fps) [MEASURED].

At the measured 116 fps, the default 64 KiB threshold is reached at roughly 22k frames, about 24 min of 15 fps footage [DERIVED]. A slower host, heavier content or `--preset slow` reaches it sooner. Drain stderr on a thread or send it to a file, or pass `-nostats -loglevel error`.

### MINOR

**m1 — `DUPLICATE_EVENT` closes corrupt both queue counts and the original event's verdict.** `swarm/overlay/compositor.py:558-566`, `591-605`
For a duplicate, the broker emits `enqueue` and then `close verdict:"DUPLICATE_EVENT"` carrying the **same** `event_id` as the original (`broker.py:557-567`). The tracker:
1. skips the duplicate `enqueue` (line 563) but removes the original queued item on the duplicate's close (lines 594-605). Measured: modeler FIFO count 0 while the broker still holds 1.
2. overwrites `close_by_event[(agent, event_id)]` (line 592). The original event's `result` cursor then shows `DUPLICATE_EVENT` instead of its real `STATE_VERIFIED` [MEASURED].

Enqueue-time refusals (`DUPLICATE_EVENT`, `QUEUE_FULL`) should not mutate FIFO state or `close_by_event`.

**m2 — Non-strict loading still crashes on a torn trailing line.** `swarm/overlay/compositor.py:304`, `324`
`json.loads(line)` runs before the `strict` gate, and `int(ts_val)` is unguarded. Composing while the broker is still appending (it writes plain `open("a")` lines, `broker.py:319-321`) raises `JSONDecodeError` [MEASURED]. Non-strict mode should skip a malformed last line.

**m3 — `compose.sh` verification does not assert two properties the brief requires.** `swarm/tools/compose.sh:164-176`
It probes `pix_fmt` but checks only `codec_name=h264` and non-zero dimensions. It never asserts `pix_fmt=yuv420p` or that `moov` precedes `mdat` (faststart). Both currently hold empirically (see the passed table), but a regression in `compositor.py:1080-1107` would go unnoticed by the wrapper.

**m4 — Recorder naming and time anchor.** `swarm/tools/record.sh:73-75`, `90`
Output names use minute resolution (`%H%M`) and ffmpeg runs with `-y`. A second take with the same name in the same minute therefore silently overwrites the first. `start_ts_ms` is sampled before ffmpeg is spawned, so the sidecar anchor runs early by the x11grab start-up latency (not measured here). Both feed M1's timeline alignment.

### NIT

- **n1** `swarm/tools/compose.sh:153`: `env DISPLAY=""` sets an empty variable rather than unsetting it (`env -u DISPLAY -u WAYLAND_DISPLAY`). Harmless, because `compositor.py:24-25` pops both, but the comment on line 152 overstates what the wrapper does.
- **n2** `swarm/overlay/compositor.py:538` claims "O(log M) lookup". The interpolation loop at `compositor.py:476-490` walks every past cursor record for every agent on every frame, which is O(M). This is not a problem at the measured 116 fps.
- **n3** `swarm/tools/record.sh:86-88`: the sidecar JSON is built from an unescaped `DISPLAY_ARG`. The host part before `:` is free text, so a `"` produces invalid JSON, which `_discover_sidecar` (`compositor.py:353-354`) then silently ignores.
- **n4** `swarm/overlay/compositor.py:330`: records are re-sorted by `ts_ms`, but CONTRACT §8.2 makes file line order the total-order authority. The real log is monotonic [MEASURED], so there is no observed effect. Ordering by `_line_no` alone would match the contract exactly.
- **n5** `swarm/overlay/compositor.py:623-625`: `resume` clears all parks, while the broker supports a targeted resume (`broker.py:634-644`). The emitted `control` record (`broker.py:655-662`, CONTRACT.md:239-243) has no `agent_id`, so the compositor cannot tell the difference. This is a contract gap, flagged for H0.

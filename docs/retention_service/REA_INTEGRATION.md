## Client call sequence

Use separate `retention_service.transport.client.Client` instances for the writer, inspector and denial endpoints. For local-open, construct `Client(None, Endpoint(unix=socket_path), validator)` with the endpoint from the generated deployment. The authority and runner use the writer endpoint and set `executor_id` to its principal. The inspector uses a fresh session on the inspector endpoint to verify stored bytes. The recovery and hold operations use the writer endpoint. Supply the admitted tenant to `Client.session(tenant)`. The session adds `Retention-Tenant` and handles HTTP framing, schema checks and wire encoding. Keep clients and their connections in the host adapter.

1. Use the session's `ready` method (`POST /retention/v1/ready`) for each required verb. It generates a fresh challenge and checks the expected principal, tenant, pins and revisions. Preview, `slot.inspect`, and joiners may probe authority and readiness, and joiners may read authorized status. The winning non-preview coordinator alone persists the request-to-attempt mapping and performs admission.
2. The authority builds the admission and sets `admission_sha256` to the SHA-256 of `retention_service.contracts.wire.admission_bytes(admission, validator)`. Use a `retention_service.contracts.validation.ContractValidator` constructed from the frozen schema directory. For launches, bind installation, slot, provider and revision, manifest and executable digests, optional adapter digest, registered source URL and executor. For compare, bind the exact ordered source IDs. Send it with `admit` (`PUT /retention/v1/attempts/{a}/admission`). Retry only the identical admission on the same owned attempt.
3. Serialize the start with `retention_service.contracts.wire.record_bytes` and pass the exact bytes and admitted request digest to `start` (`PUT /retention/v1/attempts/{a}/start`). The client checks the attempt, request and start digests in the acknowledgement. For an external launch, pass that acknowledgement to `claim` (`POST /retention/v1/attempts/{a}/launch-claim`) once. Spawn only after its verified success response. If the response is lost, inspect and preserve the unresolved outcome.
4. Pass actual payload octets, byte count, SHA-256 and a stable upload ID to `upload` (`PUT /retention/v1/attempts/{a}/uploads/{u}`). Use the verified `ObjectMeta` references in the frozen index. For source copies, the inspector verifies original bytes and the runner uploads them under the comparison attempt. Serialize the terminal with `record_bytes` and pass it and the exact artifact bytes to `finish` (`PUT /retention/v1/attempts/{a}/finish`). The client encodes the Finish envelope and checks the returned start and terminal digests. An identical retry returns the original acknowledgement. A changed, valid envelope for a sealed attempt conflicts.
5. The inspector calls `inspect` and resolves a committed `rcp_` reference with `receipt`. The client verifies the inspection bindings and canonical record digests. Use `artifact` with the terminal's expected byte count and digest, and `object_page` for each object. The client validates page offsets, sizes and digests. Reassemble the pages in order and verify the whole-object byte count and SHA-256 against the index. Use `ContractValidator.validate_index` for the frozen index and `retention_service.store.PinnedProfiles` for the inner profile and its version-specific request, attempt and operation bindings. Use `ContractValidator.validate_live_receipt_binding` on the schema reference, schema digest and receipt reference before publishing a live binding. Unknown inspection provides no receipt. The recovery principal uses `recovery` and `recovery_item` for inventory and item reads.
6. Publish references only after independently checking the live bindings, byte graph, and applicable custody and pool evidence. Parked or unavailable live routes stay closed. Keep `T01` and `T04` `PARTIAL` with `receipt_ref: null` until Carbon records `ACCEPT` against the live REA-bound receipt. The REA owner updates the request register.

## Local-open deployment

Start the Tools service in the foreground as the same OS user that runs the REA host. The default launch uses the packaged frozen schemas, which the service verifies against the existing pins. Install the Python dependencies from [the retention requirements](../../retention_service/contracts/requirements.txt).

```sh
python3 -B -m retention_service.server
```

On first run the service generates and durably publishes `viewpoint-retention/defaults.json` under `XDG_STATE_HOME` or `$HOME/.local/state`. It creates the private `store/` beside that file. The persisted defaults record the UID, GID, socket mode, tenants, principals, policy and ACL revisions, quotas and retention windows. Concurrent starts reuse the published defaults. The service exclusively locks the socket directory and durable store while running.

The service puts its sockets in `$XDG_RUNTIME_DIR/viewpoint-retention/`. When `XDG_RUNTIME_DIR` is unset, it uses the private `run/` directory beside the defaults file. Sockets are owner-only with mode `0600` [TARGET]. Both ends authenticate the peer's effective UID with Linux `SO_PEERCRED`. The selected server endpoint fixes the role for the connection. The tenant header narrows that principal's access.

| Socket | Principal suffix under `local/uid/<uid>/` | Tenant and access |
| --- | --- | --- |
| `retention.sock` | `writer` | The primary tenant `local/uid/<uid>` permits admission, start, claim, upload, finish, hold and recovery. The control tenant permits the writer to publish its positive control. |
| `inspect.sock` | `inspector` | Inspect the primary tenant through a separate authenticated connection. |
| `denial.sock` | `denial` | Inspect the control tenant `local/uid/<uid>/control`, including a committed positive control. Requests for primary evidence receive the uniform denial. |

All three endpoints share the same OS account boundary. A process running under that UID can connect to any of them. REA's host composition assigns the clients to its authority, runner and inspector roles and runs staged workloads without access to the host account or its sockets.

Local-open takes its quota and time limits from the store policy defaults. They are 1 GiB [TARGET] per object, 4 GiB [TARGET] per attempt, 64 GiB [TARGET] per tenant and 32 MiB [TARGET] for snapshots. Committed evidence expires after 30 days [TARGET]. Holds defer deletion. The purge window is 24 hours [TARGET] and the recovery snapshot lifetime is 15 minutes [TARGET].

For evidence writes, launch the service with `--witness-module "$REA_WITNESS_MODULE"` and supply the installed REA witness provider described below. `--frozen-dir` can select another copy of the same pinned schemas. An absent witness provider leaves evidence-write readiness and admission unavailable. Qualify with actual witness evidence and approved REA profile pins.

## TLS deployment opt-in

Use an explicit [server config](server.config.example.json) and the [named approval template](server.approval.example.json) for network exposure. The TLS profile requires both files. Fill in the public values and use JSON integers for the port, Unix IDs, mode, size limits and policy seconds. Use the approved signer-backed client identity with `retention_service.transport.tls.TLSContext` and `retention_service.transport.tls.Signer`. Both TLS endpoints verify the approved server DNS SAN. The approved store root must already exist and be private to the service account. Reserve the Unix path exclusively for that root and protect its parent directory. See [the transport build instructions](../../retention_service/transport/README.md).

```sh
python3 -B -m retention_service.server --config "$RETENTION_CONFIG" --approval "$RETENTION_APPROVAL"
```

The opt-in profile binds the named TCP IP before accepting requests. For an approved TLS Unix-only installation, use matching `"local_only": true` in the config and approval. The approved trust path is a public PEM CA/CRL bundle and can be rotated atomically. The ACL file is public authorization metadata. Its fields are `revision`, `credentials` (certificate `fingerprint`, `uri_san`, `principal`), `grants` (`principal`, `tenant`, `verb`, `scope`), and `comparisons` (`writer`, `inspector`, `tenant`, `destination`, `reference`, `candidate`). Scope objects can bind `request_id` and `attempt_id`. Assign inventory to an approved tenant-wide recovery role.

## REA witness provider

The installed witness module must supply `witness(kind, actor, admission, value)`, `verify_witness(kind, actor, admission, record, evidence)` and `validate_profile(admission, profile, terminal)`. In `witness`, `kind` is the string `"start"`, `"claim"` or `"finish"`. `actor` is the authenticated `retention_service.store.Actor` with string `tenant` and `principal` fields. `admission` is the durable Admission dictionary. For start, `value` is the exact start `bytes`. For claim it is the `StartAck` dictionary with string `attempt_id`, `request_sha256` and `start_sha256` fields. For finish it is a `tuple[bytes, bytes]` containing the exact terminal and artifact in that order.

Return independent evidence bound to those inputs as a JSON value whose canonical `record_bytes` encoding is at most 1 MiB [CITED: `retention_service/store/model.py`]. For start, the stored wrapper containing `start_sha256` and the evidence must fit within the same limit. Return byte-identical canonical evidence for exact start or finish retries, including after a lost reply or a `terminal_commit_interrupted` recovery. Changed evidence conflicts with the durable start, terminal or finish intent. The launch claim is single-use. Raise `ValueError` for invalid evidence or `OSError` for an unavailable witness source. The server returns HTTP 422 or 503 respectively, before the requested write.

`verify_witness` checks the original proof against the authenticated actor, durable admission and decoded record. Provide the historical verifier needed by service reopen and readback. Implement `validate_profile` with `PinnedProfiles` using the approved local schema bytes and REA's version-specific binding check. Both verification callbacks return literal `True` on success. The witness implementation, approved live profile and authenticated evidence source are REA owner dependencies.

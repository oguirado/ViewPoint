D2: combine kernel containment with pressure-aware admission
Use admission control to decide how much work may run, and cgroups v2 to contain the damage when a workload exceeds its budget. The kernel does not discover an optimal sandbox concurrency automatically: 
memory.max enforces a boundary, PSI measures time lost to contention, and a user-space controller must combine those signals with completed-work throughput and latency. This separation is supported by the kernel’s PSI documentation, the PSI-driven feedback loop in TMO, and server-driven overload control in Breakwater. kernel+3
For D2, the appropriate architecture is:text
Bounded pending-work queue
          |
          v
Node admission controller
  - memory reservations + emergency headroom
  - active-work concurrency limit
  - separate boot/restore concurrency limit
  - throughput, latency, PSI feedback
          |
          v
Sandbox-pool cgroup
  - aggregate memory boundary
  - pool-level PSI and memory events
          |
          +-- sandbox-1: memory.high / memory.max / swap.max=0 / cpuset
          +-- sandbox-2: memory.high / memory.max / swap.max=0 / cpuset
          ...
          +-- sandbox-32
This is a design synthesis, not a claim that one cited paper implements this exact combination. Nor do the sources establish that 8, 16, or 32 sandboxes is universally safe: the useful concurrency depends on the working sets, CPU allocation, storage representation, and workload phases.
1. Assign each kernel mechanism a distinct role
MechanismRole in D2Important limitation
memory.maxLast-resort per-sandbox hard memory boundary. If reclaim cannot satisfy an allocation at the limit, the kernel invokes a cgroup OOM.It is not a physical-memory reservation. Child limits can collectively exceed the parent’s capacity.  kernel
memory.highEarly pressure boundary: crossing it throttles processes and subjects them to heavy reclaim, giving the controller an opportunity to respond.Crossing it does not itself invoke the OOM killer, but reclaim stalls can severely degrade useful throughput.  kernel+1
memory.swap.max=0Prevent new swap usage by the sandbox cgroup.It removes a way to accommodate anonymous-memory pressure; it does not create extra RAM or prevent OOM.  kernel
memory.pressureMeasure memory-related stall time at sandbox and pool scope.It measures lost execution time, not bytes available or a guaranteed countdown to OOM.  docs.kernel
cpuset.cpusConstrain where sandbox threads may execute; hold the CPU topology stable during concurrency experiments.An allowed CPU mask is not, by itself, an exclusive allocation. Inspect 
cpuset.cpus.effective and configure disjoint sets or appropriate partitions if exclusivity is required.  kernel+1
memory.oom.group=1Treat an individual sandbox’s processes as one failure unit rather than leaving a partially killed workload.It is failure containment, not admission control. Tasks with 
oom_score_adj=-1000 are exceptions.  docs.kernel
A key distinction is the scope of the OOM. An OOM invoked within an individual memory cgroup does not select victims outside that cgroup. However, sibling sandboxes can still collectively exhaust an ancestor’s budget or the host, so leaf limits alone do not establish node-wide safety. kernel+1
Keep the admission controller and essential host services outside the sandbox-pool subtree. Avoid setting 
memory.oom.group=1 at the entire pool boundary unless killing the entire pool is explicitly intended: the setting applies to the selected cgroup and its descendants. docs.kernel
2. Treat 
/dev/shm as memory consumption, not free storage
/dev/shm is normally tmpfs. Tmpfs stores its contents in kernel caches and can use swap unless swap is disabled for the relevant allocation context or the mount uses the supported 
noswap option. Its 
size= setting limits allocated filesystem bytes; it does not reserve that much physical RAM. The default size, when unspecified, is 50% of physical RAM. docs.kernel
For D2, distinguish three different consumers:
Guest RAM backing.
Images, snapshots, writable root filesystems, and scratch files held in tmpfs.
VMM/container processes and their host-side overhead.
Do not assume that putting a VM’s files in 
/dev/shm accounts for its guest RAM, or that a small VMM overhead implies a small total sandbox footprint. Firecracker’s paper describes a low-overhead VMM, but that overhead is distinct from the memory assigned to the guest and from host-side image storage. usenix
Charge memory to the correct owner
Cgroup memory ownership follows allocation: a memory area is charged to the cgroup that instantiated it and remains charged there until released. Moving a process afterward does not move its existing memory charges. Consequently, images populated in tmpfs by a management process can consume a different cgroup’s budget from the VMM that later uses them. docs.kernel
Recommended D2 accounting policy:
Create private sandbox data and start the VMM/container inside its intended cgroup before substantial allocation.
Put deliberately shared images or snapshots in an explicitly budgeted image-cache ownership domain.
Count shared physical pages once in node accounting; do not assume each reader receives an equal cgroup charge.
Bound tmpfs capacity separately from sandbox memory limits.
Reconcile accounting after teardown, rather than assuming process exit means all backing storage disappeared.
That last point matters especially for tmpfs: files persist until removed or the filesystem is unmounted. Killing the writer is not equivalent to deleting its files. docs.kernel
3. Discover the throughput knee experimentally
The throughput knee is an operational choice: the region where adding active sandboxes produces little additional useful work while latency or contention rises. PSI helps identify why progress is deteriorating, but the controller still needs application-level completion measurements. The kernel explicitly describes PSI as measuring productivity loss caused by resource scarcity. docs.kernel
Use a controlled 8–32 concurrency sweep
A suitable D2 experiment is:
Test 8, 12, 16, 20, 24, 28, and 32 active sandboxes; refine around the transition.
Keep workload mix, input size, CPU allocation, NUMA placement, and cache state comparable.
Measure warm execution separately from cold boot/restore and synchronized memory-growth bursts.
Repeat runs long enough to observe representative completion times and memory peaks.
Stop the upward sweep on a safety violation rather than intentionally driving the node into OOM.

Do not use a PSI threshold alone as “the knee.” CPU, memory bandwidth, locks, and memory capacity can produce different saturation behavior; Breakwater’s use of server-side queueing delay likewise illustrates that overload control needs a signal tied to actual service progress, not just resource occupancy. usenix
4. Admit against committed memory, not just current usage
For non-swapping workloads, current usage can look safe immediately before many sandboxes fault in additional guest pages or expand tmpfs scratch simultaneously. Since 
memory.max is a limit rather than a reservation, user space must keep a reservation ledger if it wants to protect against those concurrent commitments. kernel
A proposed D2 admission invariant is:𝐵shared+∑𝑖∈𝐴𝑅𝑖+𝑅new≤𝑀physical−𝐻
where:
𝐵shared: separately accounted shared images and pool overhead.

𝐻: capacity withheld for the host, controller, accounting uncertainty, and reaction-time bursts.
For a strict “every admitted workload may reach its declared budget” policy, reserve those full budgets. Reserving only observed p99 usage is statistical overcommit: it may improve density, but it does not guarantee survival of correlated peaks.
Use a second, measurement-based guard:𝑀available>𝑅new,startup+𝐻reaction
The reservation test protects against promised future demand; the measured-headroom test protects against present accounting drift and allocations outside the ledger. These are complementary checks, not quantities to add together indiscriminately.
5. Run a fast safety loop and a slower optimization loop
Fast safety loop: close the gate before searching for efficiency
PSI supports persistent threshold monitors using 
poll()/
epoll(). Register the trigger on an open pressure-file descriptor and retain that descriptor; closing it unregisters the monitor. Per-cgroup monitors use the same interface as system-wide monitors. docs.kernel
For example, the documented trigger format is:text
some 150000 1000000
This means 150 ms of partial stall time within a one-second window. It is an interface example, not a recommended D2 threshold. Supported windows range from 500 ms to 10 seconds, so PSI notification is not a substitute for sufficient memory headroom during abrupt allocation bursts. docs.kernel
Proposed safety behavior:text
on pressure event, memory-event change, or periodic sample:
    reconcile reservations and actual memory usage

    if headroom is insufficient
       or pressure exceeds the calibrated safety threshold
       or an OOM event occurs:
        stop admissions immediately
        stop new boot/restore operations
        reduce the target active concurrency

        let healthy active work drain
        reclaim or terminate selected restartable work if necessary

    reopen only after:
        headroom exceeds a higher recovery watermark
        pressure remains below a lower recovery threshold
        the recovery interval has elapsed
Two important constraints:
Reducing the target concurrency affects future admissions; it does not immediately remove memory from already active sandboxes.
Freezing a cgroup stops its processes but does not release their memory. Ballooning, workload-specific release, migration, termination, or storage cleanup must actually return capacity. The kernel documents freezing as execution suspension, not memory reclamation. kernel
Slow optimization loop: probe cautiously
Use gradual upward probes during sustained healthy operation and larger downward adjustments when throughput deteriorates or pressure rises. Require improvement in successful throughput, not simply a larger number of running sandboxes.
Also maintain separate tokens for resident sandboxes, actively executing work, and boot/restore operations. A warm resident VM and a simultaneously restoring VM are different resource phases; the MicroVM SnapStart paper specifically studies high-concurrency restoration as its own systems problem. usenix
6. Prevent cascades at three separate boundaries
For D2, “prevent OOM cascades” should mean:
Node boundary: reservations and host headroom keep aggregate commitments away from global exhaustion.
Sandbox boundary: 
memory.max limits a runaway sandbox, and per-sandbox 
memory.oom.group=1 avoids partial-process failure.
Recovery boundary: bounded retries, restart backoff, and verified resource cleanup prevent one failure from triggering a synchronized replacement burst.
The first two follow directly from cgroup hierarchy and OOM semantics; the third is an orchestrator policy needed to avoid reintroducing overload during recovery. A leaf cgroup OOM does not itself imply cross-sandbox victim selection. kernel+1

The defensible D2 position is therefore to use these sources together: kernel documentation defines containment and observability; TMO demonstrates pressure-driven memory feedback; Breakwater demonstrates admission before overload; and the MicroVM papers explain the virtualization and restoration costs that the admission model must budget. None supplies a portable “32 sandboxes is safe” setting.

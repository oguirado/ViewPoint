D1 conclusion
Feasible, but distinguish an unprivileged VMM from a fully rootless orchestration stack:
Firecracker and Cloud Hypervisor can use KVM without running their steady-state VMM process as host root. Access to 
/dev/kvm, guest images, sockets, and any networking resources is the essential starting point—not a blanket requirement for 
CAP_SYS_ADMIN. Both projects support aarch64. docs.kernel+2
Neither requires exposing 
/dev/vhost-vsock for its native, userspace-backed virtio-vsock communication path: the guest uses 
AF_VSOCK, while the host side uses Unix-domain sockets. Firecracker explicitly describes bypassing the host’s vhost kernel code; Cloud Hypervisor adopts that hybrid implementation. There is, however, a documentation inconsistency about host kernel configuration, discussed below. github+1
Stock production orchestration is not automatically rootless. Firecracker’s jailer performs privileged setup. Kata’s “rootless VMM” mode explicitly leaves the shim and 
virtiofsd running as root. The firecracker-containerd benchmark harness also uses privileged Docker containers. None of these facts establishes a supported, end-to-end rootless Docker deployment. kata-containers.github+1
For GB10, generic aarch64 support is not a hardware qualification statement. I did not find a primary benchmark validating the complete combination “GB10 + rootless Docker + multiple VMMs + no 
/dev/vhost-vsock”. NVIDIA also explicitly states that DGX Spark GPU passthrough into virtualization environments is unsupported. CPU microVM feasibility and GPU availability inside those VMs must therefore be treated separately. docs.nvidia+1
The following is a production design assessment based on upstream documentation and inspected source, not a claim that this exact configuration has been benchmarked.
1. Production architectures
A. Host-managed launcher, unprivileged per-VM VMMstext
Linux aarch64 host
├── trusted launcher / runtime
│   ├── provisions namespaces, resource limits, images and networking
│   └── starts a distinct unprivileged VMM for each VM
├── VMM A → KVM VM A → guest kernel + workload
├── VMM B → KVM VM B → guest kernel + workload
└── per-VM Unix sockets → guest virtio-vsock agents
This is the closest match to Firecracker’s documented production security model. Upstream requires its jailer, or process constraints at least as restrictive, and recommends a distinct UID/GID for each Firecracker instance. The launcher and its inputs remain trusted. github
For your Docker requirement, the corresponding design is a trusted provisioning layer plus tightly constrained VMM containers. That provisioning layer can prepare resources outside Docker; it does not need to grant the running VMM broad host privileges.
Important limitation: this is an architectural adaptation, not an upstream recipe certifying rootless Docker as equivalent to the Firecracker jailer.

B. Direct VMM inside an unprivileged or rootless Docker containertext
Docker container
├── unprivileged Firecracker or Cloud Hypervisor
├── /dev/kvm
├── private guest images and API/vsock sockets
└── optional prepared network backend
    ├── VM A
    └── VM B
The KVM API creates a VM through an ioctl on the KVM device; subsequent VM and vCPU operations use returned file descriptors. Consequently, the same 
/dev/kvm node can serve multiple independent VMM processes—it is not an exclusively assigned physical device. A container boundary around the VMM does not itself introduce an additional virtualization level. docs.kernel
For D1, I would prefer one VMM per outer container, with multiple containers per host, rather than unrelated tenants sharing one outer container. This maps Docker’s process and resource boundary onto the VM boundary and aligns better with Firecracker’s per-process, single-tenant guidance. Multiple VMMs in one container remain possible, but Docker’s outer resource limit is then an aggregate limit unless you implement an additional per-VM mechanism. docker+1
Rootless Docker adds a separate constraint: its daemon and containers run inside user namespaces. Capabilities granted there do not confer authority over host-global resources. Host device access, UID/GID mappings and cgroup delegation must already permit the operation. docs.docker+1
C. Kata Containerstext
containerd / CRI
└── Kata shim
    ├── VMM → guest kernel
    │         └── kata-agent → workload containers
    └── agent RPC over VSOCK
Kata is an orchestration architecture for VM-isolated containers, not simply “Docker containing several VMM binaries”. Its runtime starts the hypervisor and communicates with the guest agent using ttRPC over VSOCK. github
Its documented rootless mode has a precise meaning:
Only the VMM drops privileges.
The shim and 
virtiofsd remain root.
The current guide covers runtime-rs QEMU variants and 
clh-runtime-rs.
Firecracker has no corresponding Kata 
rootless setting; the guide directs operators to the jailer. kata-containers.github
Also distinguish core hypervisor support from deployment packaging: Kata’s design documentation lists aarch64 support for Cloud Hypervisor and Firecracker, but the retrieved Helm configuration labels its Cloud Hypervisor shims as amd64. Verify the exact release artifacts and shim combination instead of assuming every deployment path supports ARM. github+1

D. firecracker-containerdtext
specialized host containerd + control plugin
└── out-of-process runtime shim
    ├── Firecracker → microVM
    └── guest agent
        └── containerd-shim-runc-v1 → runc → workload containers
Its control API models the lifecycle of a microVM that can contain multiple containers. This is different from placing multiple Firecracker processes inside a Docker container: it primarily puts workload containers inside Firecracker guests. The project requires a specialized containerd binary containing its control plugin. github
The project README explicitly says multi-tenant use cases are at the user’s own risk. Do not equate this integration’s security posture with a production Lambda/Fargate deployment merely because it uses Firecracker. github

Rootful “unprivileged Docker” is not rootless Docker
A rootful daemon can expose an individual device without 
--privileged, using 
--device. That does not mean a rootless daemon can grant access its host user does not possess. docs.docker+1
For rootless execution, validate all of these independently:
The host identity behind the VMM can open 
/dev/kvm read/write.
The device appears inside the container.
UID/GID mappings or ACLs preserve effective access.
Ancestor device restrictions and LSM policy permit access.
Seccomp permits the VMM’s actual syscall paths.
Resource limits are enforced rather than silently ignored. docs.docker+3
In particular, do not assume that 
--group-add <host-kvm-gid> has identical semantics under rootful Docker and a rootless user-namespace mapping.
3. Operating without 
/dev/vhost-vsock
Use the hybrid userspace vsock backend
For Firecracker:json
{
  "guest_cid": 3,
  "uds_path": "/run/vm-a/agent.vsock"
}
For Cloud Hypervisor:bash
--vsock cid=3,socket=/run/vm-a/agent.vsock
The communication path is:text
host/controller AF_UNIX
        ↕
userspace virtio-vsock implementation
        ↕
guest AF_VSOCK
A host-to-guest connection uses the Unix socket and a 
CONNECT <guest-port>\n handshake. Guest-to-host connections are mapped to Unix sockets derived from the configured path and destination port. github+1
This allows a control-plane-only microVM to omit a virtio-net device. General internet access would then require a separate network backend or an explicitly designed application relay; vsock does not automatically give the guest an IP network.
Use per-VM socket directories with restrictive permissions. Do not multiplex unrelated VMs onto the same pathname. Firecracker documents socket-path collisions during snapshot restoration and provides 
vsock_override to change the restored path. github
Documentation inconsistency to record in D1
Both projects’ vsock guides list host 
CONFIG_VHOST_VSOCK among prerequisites. However:
Firecracker’s same document explicitly says its implementation bypasses host vhost kernel code.
Cloud Hypervisor’s device-model document says its hybrid implementation is copied from Firecracker. github+2
Accordingly, distinguish “a documented kernel-config prerequisite” from “the VMM must open 
/dev/vhost-vsock”. The latter is not required by the described userspace socket path. For production qualification, verify this against the pinned binaries by tracing device opens and testing with the device absent.
Kata’s privileged-FD path is a different case
Kata documents that its shim opens 
/dev/vhost-vsock and 
/dev/vhost-net as root and passes descriptors to QEMU. This removes the need for the unprivileged QEMU process to open those paths; it does not eliminate host privilege from the architecture. Kata also warns that 
/dev/vhost-vsock controls a host-global CID namespace. kata-containers.github
Thus, “no device mounted into the VMM container” and “no privileged component accesses that device anywhere” are different requirements.
4. Security caveats for production
Preserve both sandbox layers
Docker’s filter and the VMM’s own seccomp filters serve different purposes and must both permit legitimate execution. Docker documents restrictions on namespace creation, mounts, 
pivot_root, 
setns, 
io_uring and other calls that can affect jailers or optional I/O paths. Cloud Hypervisor enables per-thread seccomp filters by default; Firecracker recommends its default restrictive filters for production. docs.docker+2
Do not make 
--privileged, 
seccomp=unconfined or disabling VMM seccomp the permanent solution to a startup error.
Treat the VMM control plane as privileged
Firecracker’s jailer inputs are trusted, including executable, jail and namespace paths. Those paths and their parents must not be writable by untrusted users. Separate tenant workload access from host API sockets, image selection, snapshot files and launcher configuration. github+1
KVM exposure remains host-kernel exposure
The isolation boundary still depends on the VMM, KVM, host kernel and processor virtualization features. Rootless Docker does not eliminate bugs in those components. Firecracker explicitly requires host/guest patching and firmware or microcode maintenance, and says it cannot itself mitigate all hardware vulnerabilities. github
Bound resources beyond guest RAM
Account for VMM memory, page cache, CPU, storage, file descriptors and guest-influenced logs. Firecracker specifically warns about unbounded serial/log output and noisy-neighbour storage contention, and recommends cgroups, resource limits and device rate limiters. Network egress filtering is the operator’s responsibility. github
For multiple VMs, enforce per-VM limits as well as a host-wide admission limit; an aggregate Docker limit alone cannot provide fair allocation between VMMs sharing that container.
5. ARMv9 / NVIDIA GB10 qualification
The appropriate conclusion is “aarch64-capable design, GB10 validation required”, not “ARMv9 guarantees compatibility”. Cloud Hypervisor itself says functionality varies across its supported architectures. firecracker-containerd’s Makefile contains explicit aarch64 build/kernel handling, but that is not a GB10 qualification result. github+1
A useful host inventory is:bash
uname -m
uname -r
getconf PAGESIZE
ls -l /dev/kvm
id
docker info

grep -E 'CONFIG_(KVM|ARM64_.*PAGES|SECCOMP|SECCOMP_FILTER|CGROUPS)=' \
  "/boot/config-$(uname -r)"
Then qualify the exact combination:
Selected VMM release, host kernel and aarch64 guest kernel.
Successful guest boot and agent RPC with 
/dev/vhost-vsock absent.
Actual host and guest page granules, rather than assuming every ARM system uses the same base page size.
The selected guest’s required virtio transports and devices.
Enforced memory/CPU limits under concurrent load.
Snapshot/restore support on that release and CPU configuration.
These are proposed acceptance checks, not claims that a particular GB10 kernel is known to fail them.
For GPU workloads, the authoritative boundary is clearer: NVIDIA’s DGX Spark support page states that GPU passthrough for virtualization environments is unsupported. NVIDIA’s documented Docker/container support must not be interpreted as GPU support inside a microVM. docs.nvidia+1

The primary historical suite is Kata metrics methodology, with time, density, network, storage and disk tests.
Its documentation distinguishes stable CI regression measurements from maximum-performance measurements. It targets no more than 5% run-to-run variation and five minutes per test for PR checks; these are methodology targets, not measured GB10 performance.

7. Recommended D1 decision
My engineering recommendation is:
Use native userspace virtio-vsock over private Unix sockets; exclude 
/dev/vhost-vsock from the VMM execution environment.
Prefer one VMM per outer container and one tenant per VM/VMM process.
Begin with file-backed guest storage and no guest network device. Add networking only through a separately qualified backend.
Keep host-global provisioning in a small trusted component; keep capabilities out of steady-state VMM processes.
If fully rootless operation is non-negotiable, classify it as a custom integration requiring qualification—not a capability already proven by Kata’s rootless-VMM setting or firecracker-containerd’s Docker harness.
Gate production on GB10 measurements of concurrent boot-to-agent-ready latency, application-ready latency, total host memory, sustained CPU/I/O contention, cleanup after failures, and isolation of API/vsock endpoints.
This follows the upstream distinction between privileged setup and unprivileged execution, Firecracker’s per-process tenant guidance, and the benchmark suites’ actual measurement scopes. It does not rely on generic microVM boot-time claims as evidence for the complete D1 architecture. kata-containers.github+3

For D1, the defensible design is a single locked build graph with multiple artifact exporters—not “a Dockerfile plus a rootfs conversion script” that independently resolve dependencies. BuildKit supplies a content-addressed execution graph and image exporters; Nix supplies declared dependency closures and sandboxed builds; Kata supplies guest-OS assembly conventions; EROFS/SquashFS serialize a root filesystem; dm-verity authenticates its blocks at runtime. None of these, individually, guarantees both bit reproducibility and exclusion of ambient host state. Those are separate properties that must be enforced and verified. kernel+3
The crucial distinction is hermeticity: preventing undeclared inputs from reaching a build. Reproducibility asks whether rebuilding produces identical bytes; dm-verity asks whether runtime blocks match a trusted digest. Two builds can identically leak the same secret, and dm-verity will faithfully authenticate that contaminated image. BuildKit’s own 
reproducible=true provenance field is a user-supplied assertion, not a successful independent rebuild test. kernel+2
1. One declarative recipe, one locked input graph, several outputs
A suitable D1 architecture is:text
Committed recipe + dependency locks + source commit + target platform
                                │
                     hash-verified input acquisition
                                │
                  isolated evaluation and build execution
                                │
                       declared package closures
                         ┌──────┴──────┐
                         │             │
                environment tree   guest OS tree
                         │         + init/Kata agent
                         │             │
                  OCI image       EROFS or SquashFS
                                       │
                              dm-verity hash tree
                                       │
                          trusted root hash + boot policy
This is a proposed composition of the documented mechanisms, not a common format implemented by all four projects. BuildKit’s LLB graph records execution steps and dependencies; Nix builds derivations; Kata explicitly separates rootfs-tree creation from disk-image or initrd creation. docker+2
The recipe and lock data should determine:
Source commit and dependency content hashes, including submodules and downloaded archives.
Nixpkgs revision or digest-pinned container bases, plus the Dockerfile frontend.
Compiler, linker, filesystem builder, compression libraries, and builder/exporter versions.
Target architecture, CPU-feature policy, locale, timezone, timestamps, ownership, permissions, and filesystem layout.
OCI export/compression settings and dm-verity parameters.
BuildKit documents source policies for replacing mutable image references with digests and HTTP inputs with checksums. Its reproducibility documentation also shows why exporter behavior and compression versions belong in the reproducibility boundary. Nix pure evaluation separately restricts evaluation to declared inputs rather than ambient state. nix+1
Use the commit as a lookup label, not as the artifact’s sole identity. A useful proposed identity is:text
build-key = hash(recipe, locks, source, platform, export-policy)
artifact-id = hash(actual output bytes)
A changed platform or dependency lock can legitimately change the result for the same application commit. Conversely, two commits can legitimately produce the same environment image when their environment inputs are unchanged.
Primary documentation: BuildKit reproducibility, Nix configuration and purity controls, and Kata osbuilder. nix+2
2. Excluding host paths requires controlling the client, evaluator, and worker
Sandboxing only the compiler is insufficient. The build client can first read host configuration, forward an SSH agent, or import a host directory into the declared build context. Once imported, that material is no longer “outside” the worker sandbox. Docker documents automatic SSH-agent use for SSH Git contexts; Nix documents user configuration discovery under 
$HOME/.config/nix and configuration supplied through environment variables. nix+1

3. Producing bit-identical OCI environment images
BuildKit’s documented timestamp controls are necessary, but not sufficient:
Set 
SOURCE_DATE_EPOCH deterministically from source or packaging metadata.
Pass it explicitly as a build argument.
Use 
rewrite-timestamp=true to normalize timestamps inside exported image layers.
Pin base images, frontend, BuildKit version, platform, media-type behavior, and compression policy.
Make the commands inside 
RUN reproducible too—timestamp rewriting cannot repair nondeterministic file contents. reproducible-builds+1
An illustrative export invocation, executed inside the controlled launcher described above, is:text
docker buildx build \
  --platform=linux/amd64 \
  --network=none \
  --build-arg SOURCE_DATE_EPOCH="$COMMIT_EPOCH" \
  --provenance=false \
  --sbom=false \
  --output \
"type=oci,dest=environment.oci.tar,rewrite-timestamp=true" \
  "$CLEAN_SOURCE_CONTEXT"
The timestamp/export options follow BuildKit’s documented reproducibility mechanism. The recipe still needs digest-pinned inputs, deterministic build commands, and an enforced mount/input policy; this command alone does not establish those properties. docs.docker+1
Separate reproducible payloads from execution evidence. Provenance includes invocation IDs and build start/finish times, so attaching it can change an enclosing index or archive even when the application image is unchanged. Retain provenance as separately verified evidence bound to the payload digest, or explicitly exclude its changing envelope from the reproducibility comparison. Do not discard provenance altogether. docker
Define the comparison precisely:
Identical unpacked files are weaker than identical layers.
Identical layer contents are weaker than identical compressed blobs and image configuration.
Comparing an OCI archive byte-for-byte additionally tests archive packaging and attached metadata.
BuildKit’s documentation explicitly distinguishes timestamp locations and digest-affecting exporter behavior; D1 should specify which complete artifact bytes must match. github
The normative timestamp source is the SOURCE_DATE_EPOCH specification. It requires a deterministic, source-derived value and explicitly warns that Git does not normalize working-tree file timestamps by itself. reproducible-builds
4. Kata builders: reuse the graph, not the workstation
Kata osbuilder is a guest-OS assembly tool, not an automatic reproducibility guarantee. Its documentation says:
The 
distro method uses distribution tools such as 
debootstrap or 
yum.
Components run on the host by default unless their containerized mode is selected.
The 
dracut method deliberately incorporates required host-side filesystem components.
A rootfs tree is subsequently converted into an image or initrd. github
For D1:
Run the builder in a pinned, isolated build environment.
Lock distribution repositories and package inputs rather than resolving “latest” packages during assembly.
Supply the Kata agent, init configuration, libraries, and guest-kernel module set as declared inputs.
If using dracut, make its apparent “host” a declared build environment, not the developer workstation.
Treat upstream examples using 
sudo -E PATH=$PATH as convenience instructions, not as a host-environment exclusion policy. github
The container environment and guest OS need not contain identical files. They should derive from the same dependency and policy graph, with explicit differences: the guest requires boot/init and Kata-agent integration, whereas an OCI development environment may require different entrypoints and tools. docs.docker+1
5. Deterministically serializing EROFS or SquashFS
First create a canonical guest tree: fixed numeric ownership, intended permissions, explicit xattr policy, stable timestamps, and only declared files. Then serialize it with pinned filesystem and compression tools. SquashFS upstream explicitly identifies source contents, inode metadata, root-directory metadata, and filesystem creation time as conditions for byte-identical output. github
EROFS
An illustrative invocation for an all-root-owned tree is:text
mkfs.erofs \
  -T "$SOURCE_DATE_EPOCH" \
  --all-time \
  -U "$ROOTFS_UUID" \
  --all-root \
  guest.erofs rootfs/
Use a fixed or deterministically derived UUID, never a randomly generated one. EROFS documents 
-T, 
--all-time, and 
-U; compression is optional and should be explicitly configured and pinned if enabled. If the guest needs non-root owners, encode those owners deliberately instead of using 
--all-root. manpages.debian+1
Primary documentation: EROFS image construction and the mkfs.erofs manual. manpages.debian+1
SquashFS
For a pinned version supporting the documented options:text
mksquashfs rootfs/ guest.squashfs \
  -noappend \
  -all-root \
  -comp xz \
  -b 131072 \
  -repro-time "$SOURCE_DATE_EPOCH"
Upstream documents 
-repro-time as setting both filesystem creation time and inode timestamps. Older versions expose related controls as 
-mkfs-time and 
-all-time; do not assume option names or compressor behavior are interchangeable across versions. github+1
Primary documentation: SquashFS upstream mksquashfs usage. github
6. Adding dm-verity without reintroducing randomness
dm-verity operates below the filesystem. Its deterministic inputs include the exact data bytes, hash-format version, hash algorithm, salt, data/hash block sizes, data length, and hash-tree placement. A verity superblock also introduces a UUID unless supplied explicitly. kernel+1
After deterministically zero-padding the filesystem image to the selected data-block boundary, a separate-tree construction can use:text
veritysetup format \
  --format=1 \
  --hash=sha256 \
  --data-block-size=4096 \
  --hash-block-size=4096 \
  --salt="$DECLARED_VERITY_SALT" \
  --uuid="$DECLARED_VERITY_UUID" \
  --root-hash-file=guest.roothash \
  guest.erofs guest.verity

veritysetup verify \
  --root-hash-file=guest.roothash \
  guest.erofs guest.verity
Both salt and UUID must be declared deterministic inputs. Alternatively, 
--no-superblock removes the persistent header, but then verification and activation must receive the same parameters used for formatting. 
veritysetup verify performs userspace verification without creating a kernel mapping. man7
At boot, mount the filesystem through the verified mapper device—not directly through its underlying block device—and provide writable state separately. The kernel must have the selected filesystem and dm-verity support available during boot. The root hash must be authenticated through a trusted boot/configuration path; placing an unauthenticated root hash beside the image provides no protection against replacing both. kernel
The kernel specification explicitly states that dm-verity is read-only and that the root hash must be trusted. It also documents optional PKCS#7 root-hash verification. Do not enable 
ignore_corruption in a policy intended to reject tampering. kernel
Primary specifications: Linux dm-verity construction and on-disk behavior and the upstream veritysetup manual. kernel+1
7. What D1 can actually prove—and the verification gate
The defensible claim is conditional:
Given the reviewed launcher, effective worker configuration, declared inputs, and trusted isolation implementation, build processes have no permitted route to the developer’s home/configuration files, agent sockets, or undeclared environment. Independent rebuilds then test whether those declared inputs produce identical artifact bytes.
